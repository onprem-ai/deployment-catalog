**Goal:** Test vLLM v0.17.1 with SM120 fixes and resolve deployment issues

**Findings:**
- vLLM v0.17.1-cu130 includes SM120 NVFP4 MoE fix (PR #33417)
- MoE backend correctly selects `FLASHINFER_CUTLASS` instead of MARLIN fallback
- Model loads successfully: 71.32 GiB in ~26 seconds
- Initial deployment failed with `AssertionError: num_cache_lines >= batch` in `causal_conv1d_update`
- Root cause: CUDA graph capture size (default 512) larger than mamba cache size
- Fix: Add `--max-cudagraph-capture-size 128` (or smaller)
- Also needed: `--gpu-memory-utilization 0.90` and `--max-model-len 32768` for VRAM headroom

**Outcome:** Success - NVFP4 working on SM120 with proper configuration

**Working configuration:**
```bash
docker run --gpus all --ipc=host \
  -v /path/to/model:/model \
  -e VLLM_FLASHINFER_WORKSPACE_BUFFER_SIZE=629145600 \
  -e VLLM_FLASHINFER_MOE_BACKEND=latency \
  vllm/vllm-openai:v0.17.1-cu130 \
  --model /model \
  --quantization compressed-tensors \
  --kv-cache-dtype fp8 \
  --trust-remote-code \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.90 \
  --max-cudagraph-capture-size 128
```

**Recommended Configuration:**

- Quantization: `compressed-tensors` (NVFP4 format)

  - `VLLM_FLASHINFER_WORKSPACE_BUFFER_SIZE=629145600` (600MB, model needs ~536MB)

**Known Issues:**
- Cannot use larger cudagraph capture sizes (>128) due to hybrid GDN architecture
- Full 262k context not achievable on 96GB VRAM with current settings
- Inference outputs include thinking process by default (model characteristic)

**Why `--max-cudagraph-capture-size` is required:**

Qwen3.5 uses a hybrid architecture combining:
1. **Gated DeltaNet (GDN)**: Linear attention with causal convolution (Mamba-style)
2. **MoE**: 122B total params, ~10B activated

The GDN components use `causal_conv1d` which has constraints on the relationship between batch size and cache lines. The default cudagraph capture size of 512 exceeds the mamba cache size, triggering an assertion error. Reducing to 128 or lower resolves this.
