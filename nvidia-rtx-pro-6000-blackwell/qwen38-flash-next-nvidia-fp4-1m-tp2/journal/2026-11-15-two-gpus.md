# 2026-11-15 - Two GPUs: the One-GPU Profile with Tensor Parallel 2

**Goal:** Serve the same checkpoint and 1M context on two RTX PRO 6000 Blackwell GPUs, to
hold more KV cache and more requests at once than the one-GPU profile
(`qwen38-flash-next-nvidia-fp4-1m`, journal of 2026-11-15 there for every step).

## Derived from the one-GPU profile

Everything is the one-GPU profile's, with these changes:

- `--tensor-parallel-size 2`. The community's TP1 and TP2 commands for this model
  (local-inference-lab/rtx6kpro, `models/qwen38-flash-next.md`) differ only in this flag.
- `--max-num-seqs 32` instead of 16: the one-GPU benchmark's decode stopped at 16 requests,
  and two GPUs hold several times the KV cache.
- Two GPUs reserved and booked; routing name `qwen3.8-flash-next-1m-tp2`.

The image, weights (same revision), environment, YaRN override and engine booking per GPU
(93 GiB) are unchanged.

## First benchmark cancelled: decode collapses above 16 requests

Job `fdcaf2c9-e28e-49a7-ab85-4abfdd280136` was cancelled during `max-decode/1.1.0`:

| Requests | Decode tokens/s | ITL p50 |
|---|---|---|
| 1 | 271 | 3.4 ms |
| 8 | 971 | 7.8 ms |
| 16 | 1,290 | 11.6 ms |
| 20 | 310 | 62.5 ms |
| 24 | 367 | 64.9 ms |

No request failed. The cause read from the settings: MTP verifies 3 draft tokens plus one,
so each sequence runs 4 tokens per decode step. NVIDIA's `--max-cudagraph-capture-size 64`
covers 16 sequences exactly (16 x 4 = 64); at 20 sequences (80 tokens) the step runs outside
CUDA graphs and each token takes about five times as long. The one-GPU profile never crossed
this line: it serves at most 16 sequences.

Change: `--max-cudagraph-capture-size 128` (32 sequences x 4), so every batch up to the
profile's 32 sequences runs in CUDA graphs. Everything else unchanged. The benchmark runs
again on a new replica.

## Tuning round: 64 sequences

Decode stopped growing at 32 requests (1,663 tokens/s), the profile's `--max-num-seqs 32`,
with 6.5 million KV cache tokens mostly unused. Change: `--max-num-seqs 64`, and with it
`--max-cudagraph-capture-size 256` (64 sequences x 4 tokens per MTP step), so the batches
stay in CUDA graphs. Everything else unchanged. Result below.

### Result: decode up, then the engine ran out of GPU memory

Replica `0fb8e7d9-04c1-45b8-afa7-766d4c20a9f7` (start-up per GPU: weights 37.74 GiB, CUDA
graphs 1.07 + 0.74 GiB, KV cache 49.53 GiB, 6,482,768 tokens). Job
`453c421f-0f9d-4715-bfa5-05fea56e9ea3`:

- `max-decode/1.1.0`: 1,654 at 32, 1,815 at 40, 1,950 at 48, **2,162 at 64** (ITL p50
  29.1 ms), 2,103 at 80; no failure. Up to 24 requests the same as with 32 sequences.
- `mixed-load/1.1.0` failed at 40 requests: the engine stopped
  (`EngineDeadError`, HTTP 500 in the stream). The inference node restarted the replica
  (error report `01a1dfb3-5c31-711a-a651-18b807cbaea6`, health check timeout).
- Peak `vram_used_bytes` 94.92 GiB per GPU, at the edge of the 95 GiB booking.

The engine's own output: the error report keeps the last 5,000 container lines, all of them
the API server's follow-up errors, so the cause was not in it. Running the load generator's
`mixed-load/1.1.0` again against the restarted replica directly on `ain-4euk3`, with the
container's output followed, reproduced it at 2 requests:

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 118.00 MiB. GPU 0 has a total
capacity of 94.97 GiB of which 111.50 MiB is free. ... 91.78 GiB is allocated by PyTorch
```

in a dense GEMM (`b12x_unquantized_gemm`) during a prefill of 8,069 tokens. The engine's
share (93 GiB, 0.9729) left too little room for activations once the graphs for 64 sequences
were captured. With 32 sequences the same share passed.

### Next round: engine booking 91 GiB

`engine_memory_booking_bytes_per_device` 93 to 91 GiB: the deploy gives vLLM 2 GiB less, the
KV cache shrinks by that, and the room stays free for activations. Sequences 64 and capture
size 256 unchanged.

### Lesson for the next round

After a change that fixes one workload, run that workload alone with the load generator
(`-workload mixed-load/1.1.0`, about 15 minutes) and the full benchmark only once it passes;
here the full run repeated 40 minutes of prefill and decode already measured.

## Published name

Measured as a test name; published as `qwen3.8-flash-next`, the name of the profile this one
replaces (`qwen38-flash-next-nvfp4`, community checkpoint), so clients keep working. Only the
