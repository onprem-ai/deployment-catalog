# 2026-11-27 14:15 Context limit and host RAM on two GPUs

**Goal:** check the 1M context the card was set to, and the host RAM it needs.

## Findings

- With `--context-length 1048576` and a KV pool of 2,082,304 tokens the engine starts, but a long prompt
  kills it: a request of about 256,000 prompt tokens ends the container with exit code 137 (SIGKILL)
  after about a minute, with no error line in the console log (the last lines go down with the kill).
  The inference node restarts it.
- **It is not host RAM.** With the container limit raised to 56G and the card alone on the node, the
  SGLang processes' RSS rose from 6.7 GB idle to at most 15.2 GB (host 18.7 GB of 63 GB) during the
  long requests, far below the limit; the control plane recorded no memory-limit hit. The crash is in
  the engine at long context (most likely a fixed-size buffer of the sparse-attention prefill), between
  213k and 256k tokens.
- **Fresh prompts only count.** The first search reused SGLang's prefix cache (a fixed-seed haystack):
  after a 160k request, a "200k" request took 29 s because most of it was cached, so it did not test a
  200k prefill. The test that counts sends every request unique from its first token (a random nonce
  sentence first, a fresh random haystack) and records SGLang's `cached_tokens`:

| Real prompt tokens | Cached tokens | Result |
|---|---|---|
| 170,532 | 0 | needle found, 51 s |
| 213,307 | 0 | needle found, 59 s |
| about 256,000 | 0 | engine killed (exit 137) |

A fresh request of about 235,000 tokens was killed as well, so the limit lies between 213,307 (tested,
fresh) and about 235,000 prompt tokens. The engine's prefill throughput on these long fresh prompts was
3,300-3,600 tokens/s; one 170k prompt took 51-61 s to its answer.

## What the card states

- `--context-length 204800` and `max_context_length: 204800` (200 Ki): below the largest fresh prompt
  that worked, with room for the answer. The final cards passed fresh needles at 6.9k, 54k, 102k and
  170k prompt tokens (4/4 each, 0 cached tokens).
- The KV pool stays at 2,082,304 tokens: with 200k per request it holds the 8 parallel requests at about
  250k tokens each, or ten 200k contexts.
- Container memory limit 32G and `host_bytes` 32 GiB: one card's processes peak at 15.2 GB RSS on long
  prompts, so two cards side by side on one node need about 36 GB of 61 GB.
- With the shorter context the CUDA graphs take 0.31 GiB instead of 0.87 GiB (their workspace scales
  with the context length); the measured memory in `ai-deploy.yaml` is that start's.
- The cause is below ("Why the long prompts crash").

## Why the long prompts crash (evidence, read afterwards from logs and metrics)

| Crash (UTC) | Setting | Exit | GPU memory per GPU, before -> last sample | Host / container RSS peak |
|---|---|---|---|---|
| 10:03 | 900k-token request, 1M context, 32G | 137 | -> 95.47 GiB | container 14.4 GB (metrics) |
| 10:19 | about 256k, 1M context, 32G | 137 | -> 94.86 GiB, then 0.62 | - |
| 13:12 | about 256k, 1M context, 56G, alone | 137 | 91.84 -> 95.37 GiB | 14.4 GB RSS, host 17.8 GB |
| 13:21 | about 256k fresh, 56G | 137 (health check then reset) | 95.0-95.5 GiB | 15.2 GB RSS, host 18.7 GB |
| 13:27 | about 235k fresh, 56G | 137 (health check then reset) | 91.84 -> 94.31 -> 95.54 GiB | - |

GPU memory from the control plane's metrics (`onprem_ai_gpu_vram_used_bytes`, 15 s samples); host RSS from
`rss_sampler.sh` on the node. The inference node did not stop the container: it reports the exit
afterwards, and for the last two the health check found the port already reset. The control plane
recorded no container memory-limit hit; the kernel log needs root on the node and was not read. The
console logs the control plane keeps end with the engine's start (at ready), so the engine's last lines
before the crash are not kept, and the KV pool usage at the crash is not logged.

**Conclusion: GPU memory, not host RAM.** In every crash each GPU of the replica filled to its physical
limit (95.6 GiB) during the long prefill, from about 91.8 GiB idle, and the engine then died with SIGKILL
(SGLang ends its whole process tree when a scheduler process dies). The KV pool is allocated at start
and does not grow, so the growth is working memory of the prefill that scales with the context length:
with 2,048-token chunks the sparse-attention indexer scores each chunk against all earlier tokens, and
the compressed-KV and indexer state of the whole context is touched per chunk. The free headroom after
start (3.8 GiB with 1M context, 4.5 GiB with 200k) is used up between 213k and 235k tokens. Which buffer
exactly is not visible without the engine's traceback.

**What would raise the limit:** more headroom per GPU, or less working memory per chunk:
`--chunked-prefill-size 1024` (halves what scales with chunk x context; prefill slower), or a lower
`--mem-fraction-static` (each 0.01 frees about 0.96 GiB per GPU at the cost of about 0.6M KV tokens;
0.93 would leave about 1.4M tokens and roughly double the headroom). Each needs a fresh long-prompt test
before the context is raised; until then the cards stay at 200k, which the engine now enforces (a longer
prompt is refused with HTTP 400 instead of crashing the engine).
