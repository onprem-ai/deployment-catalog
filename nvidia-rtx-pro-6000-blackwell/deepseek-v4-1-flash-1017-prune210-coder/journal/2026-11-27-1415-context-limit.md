# 2026-11-27 14:15 Context limit and host RAM on two GPUs

**Goal:** check the 1M context the card was set to, and the host RAM it needs.

## Findings

- With `--context-length 1048576` and a KV pool of 2,082,304 tokens the engine starts, but a long prompt
  kills it: a request of about 256,000 prompt tokens ends the container with exit code 137 (SIGKILL)
  after about a minute, with no error line in the console log (the last lines go down with the kill).
  The inference node restarts it.
- **It is not host RAM.** With the container limit raised to 56G and the card alone on the node, the
  SGLang processes' RSS rose from 6.7 GB idle to at most 15.2 GB (host 18.7 GB of 63 GB) during the
  long requests, far below the limit; the control plane recorded no memory-limit hit. The crash is in
  the engine at long context (most likely a fixed-size buffer of the sparse-attention prefill), between
  213k and 256k tokens.
- **Fresh prompts only count.** The first search reused SGLang's prefix cache (a fixed-seed haystack):
  after a 160k request, a "200k" request took 29 s because most of it was cached, so it did not test a
  200k prefill. The test that counts sends every request unique from its first token (a random nonce
  sentence first, a fresh random haystack) and records SGLang's `cached_tokens`:

| Real prompt tokens | Cached tokens | Result |
|---|---|---|
| 170,532 | 0 | needle found, 51 s |
| 213,307 | 0 | needle found, 59 s |
| about 256,000 | 0 | engine killed (exit 137) |

A fresh request of about 235,000 tokens was killed as well, so the limit lies between 213,307 (tested,
fresh) and about 235,000 prompt tokens. The engine's prefill throughput on these long fresh prompts was
3,300-3,600 tokens/s; one 170k prompt took 51-61 s to its answer.

## What the card states

- `--context-length 204800` and `max_context_length: 204800` (200 Ki): below the largest fresh prompt
  that worked, with room for the answer. The final cards passed fresh needles at 6.9k, 54k, 102k and
  170k prompt tokens (4/4 each, 0 cached tokens).
- The KV pool stays at 2,082,304 tokens: with 200k per request it holds the 8 parallel requests at about
  250k tokens each, or ten 200k contexts.
- Container memory limit 32G and `host_bytes` 32 GiB: one card's processes peak at 15.2 GB RSS on long
  prompts, so two cards side by side on one node need about 36 GB of 61 GB.
- With the shorter context the CUDA graphs take 0.31 GiB instead of 0.87 GiB (their workspace scales
  with the context length); the measured memory in `ai-deploy.yaml` is that start's.
- Open: what kills the engine above about 213k tokens. A run with the engine's own logging of the
  scheduler process (or a fault handler that writes the stack to stderr before the kill) would show it.
