# 2026-11-22 - 1M Context on Two RTX PRO 6000: KV Pool 1.63M Tokens

**Goal:** serve the checkpoint's full 1,048,576-token context instead of 262,144, on the same
two GPUs and the same vLLM nightly, without changing the weights or the image.

## Setup

- A 4x RTX PRO 6000 Blackwell Server Edition host (97,887 MiB each; two used,
  TP2 + EP), 61 GB host RAM.
- Image and weights unchanged: `vllm/vllm-openai:nightly-153dc046...` (vLLM 0.34.0rc1.dev398,
  FlashInfer 0.7.4), `deepseek-ai/DeepSeek-V4-Flash-Vision-Exp` at `6821d6ad`.

## Why 262k was not the limit

DeepSeek V4's KV cache is small: one 1M-token request needs 10.06 GiB of fp8 KV (about 10 KB per
token). The old card had 11.2 GB of KV per GPU but a pool of only 265,715 tokens, because
vLLM keeps a constant state per possible request (sliding-window cache, compressor rings), and
the card allowed 96 requests, and because the 8192-token prefill chunk and the CUDA graphs up
to the default size took memory.

## Three starts

1. `--max-model-len 1048576 --max-num-seqs 8 --max-cudagraph-capture-size 32
   --gpu-memory-utilization 0.98`: failed in CUDA graph capture with "attention workspace
   insufficient for resolved plan". vLLM gives FlashInfer's SM120 sparse-MLA kernel a fixed
   128 MiB workspace that capture cannot grow; TP2 needs about 4.1 MiB per decode token, so
   32 tokens do not fit (the fork alexbi29/vllm makes it configurable,
   `VLLM_DSV4_FLASHINFER_WORKSPACE_MB`; the upstream nightly has no knob).
2. Graphs up to 28 tokens: capture passed, then "10.06 GiB KV cache is needed, larger than
   the available KV cache memory (8.98 GiB)"; vLLM kept 1.81 GiB for transient activations.
   That start would have served 753,152 tokens.
3. `--max-num-batched-tokens 4096` (activations 1.81 -> 1.14 GiB), `--max-num-seqs 4`,
   graphs up to 16 tokens (4 requests x (1 + 3 DSpark tokens)): ready.
   `GPU KV cache size: 1,626,770 tokens, Maximum concurrency for 1,048,576 tokens per
   request: 1.55x` (10.79 GiB of KV per GPU).

## Answers (temperature 0, through the API gateway)

- Six multiplications: 6/6. The model reasons before it answers: with `max_tokens` 32 the
  reasoning used 30 tokens and cut the answer (finish_reason `length`); give clients room.
- Image (left half red, right half blue): "left: red, right: blue".
- Hidden code in filler text: 239,912 prompt tokens (depth 35 %) correct in 31 s;
  600,223 tokens (48 %) correct in 94 s; **1,019,664 tokens (32 %) correct in 221 s**
  (about 4,600 tok/s on average over the whole prompt).

## Memory

- GPU: 95,057 MiB per GPU at READY; **96,733 MiB after the 1M request**, 477 MiB over the
  94 GiB booking (96,256 MiB): the activation memory of a 1M prefill grows past what vLLM keeps
  at start. Either lower `--gpu-memory-utilization` to 0.975 (about 0.5 GiB less; the pool
  still holds one 1M request: about 10.3 GiB against 10.06 GiB) and measure again, or book
  95 GiB and accept that a GPU of this product shows 94.97 GiB free (no margin).
- Host: about 9 GB used by the replica; 52 GB available on the host during the 1M request.

## Requests at the same time: 4, 8, then 6

- `--max-num-seqs 8` with CUDA graphs up to 28 tokens: KV pool 1,613,540 tokens (4 requests:
  1,626,770). The per-request state is small: 8 instead of 4 requests cost 0.8 % of the pool.
- But 7 and 8 parallel requests ran at about 20 tok/s each, against 65 tok/s at 6. vLLM captures
  graphs at 1, 2, 4 and multiples of 8 tokens, so with a maximum of 28 the largest graph is 24
  tokens (6 requests x (1 + 3 DSpark tokens)); batches of 28 and 32 tokens ran without a full
  graph.
- Final setting: `--max-num-seqs 6`, `--max-cudagraph-capture-size 24`. KV pool 1,617,622 tokens,
  1.54 full 1M requests. Booking 95 GiB (the measured peak after a 1M request is 94.47 GiB).
- Under parallel load, one temperature-0 answer reasoned past 600 tokens and returned no content
  (finish_reason `length`); alone the same request answers in 160 reasoning tokens. Batching
  changes the path at temperature 0; no wrong answer was seen.

## Platform benchmark of the final setting (2026-11-22 evening, no failed requests)

| | 1M, 6 requests (this setting) | 262k, 96 requests (card before) |
|---|---|---|
| max-decode, c = 1 / 2 / 4 / 8 | 156 / 254 / 363 / 445 tok/s | 164 / 266 / 365 / 541 tok/s |
| max-decode plateau | about 440 tok/s from c = 8 (only the queue grows) | 2,613 tok/s at c = 96 |
| max-prefill, c = 1 / 8 | 7,167 / 10,900 tok/s | 6,623 / 9,568 tok/s |

Up to 4 parallel requests decode is unchanged; the plateau is the cost of 6 requests.

## Future optimization: a larger FlashInfer workspace (more requests at 1M)

Idea: build an image (like onpremai/sglang-dsv41-disk-engram) with a vLLM patch that makes the
SM120 FlashInfer sparse-MLA workspace configurable (alexbi29/vllm commit cfab97b,
`VLLM_DSV4_FLASHINFER_WORKSPACE_MB`; not in upstream vLLM on 2026-11-22). With a larger
workspace, CUDA graphs can be captured for more tokens, so `--max-num-seqs` can rise to about
16-32 while the maximum context stays 1M.

What it gives, and what it does not:
- More requests decoding at the same time: about 16-32 instead of 6, total decode probably
  1,500-2,000 tok/s instead of about 445 (estimate, not measured).
- Not a larger KV cache. The pool stays about 1.5-1.6M tokens in total, shared by all requests:
  for example 32 requests of 50k tokens, or one 1M request plus a few short ones. Several very
  long requests at once (3 x 500k) fit no better than today; that needs DCP (KV split across both
  GPUs, about half the speed per request) or more GPUs.
- So: many users and long context in one card, but not many users each with long context.

Drawbacks to check first:
1. KV memory: the workspace needs about 4.1 MiB per graph token at 1M context (fork's figure;
   128 tokens: about 525 MiB instead of 128 MiB per GPU), plus more graph sizes (estimate
   0.2-0.4 GiB). The pool would drop from 10.70 GiB to about 10.0-10.2 GiB against the 10.06 GiB
   one 1M request needs. If it does not fit: graphs up to 64-96 tokens (16-24 requests), or a
   maximum context of about 950k.
2. A full pool makes vLLM preempt and recompute requests: long sessions then wait suddenly.
3. Per-request decode falls under high load (about 156 tok/s alone, about 50-60 tok/s at 32).
4. An own image to maintain: review the third-party patch, port it to every new vLLM nightly
   until upstream has the fix, and test again (1M needle, high concurrency).
5. More graph sizes add about 30-60 s to the start.

Plan if taken up: calculate the KV pool for graphs up to 64, 96 and 128 tokens, pick the largest
that still holds one 1M request, build the image, then the 1M needle test, a concurrency test and
the platform benchmark.
