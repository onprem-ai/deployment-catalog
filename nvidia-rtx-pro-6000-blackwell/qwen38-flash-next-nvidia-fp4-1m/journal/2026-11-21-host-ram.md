# 2026-11-21 Host RAM per replica: the PLE table, the booking and the limit

Measured on a copy of this profile in a catalog without an upstream (`drafts`), on one RTX PRO 6000 Blackwell Server
Edition of a host with 61.6 GiB of RAM and 10 GiB of swap, with no other model loading or running on the host.
The container ran the profile's command and environment unchanged, with the memory options of the compose before this
change (`limits.memory: 48G`). Its image is a derivative of the pinned one: the same engine files, with this profile's
kernel caches baked in and libraries this model never loads removed, so the start took about 5.5 minutes instead of about 22.
This commit changes only the memory figures below.

## What holds the host RAM

`VLLM_PLE_CPU_OFFLOAD: "1"` keeps the PLE n-gram table in host memory. The engine logs it when it starts:

```
b12x_ple.py:369  Using 26.82 GiB of private CUDA-mapped host memory for this TP rank's PLE table
```

- It is allocated when the engine initializes, before the weights are read (+85 s after the container start), and it
  stays constant afterwards: the same engine process still held it after 11 h 40 min. It is not loader staging memory.
- Engine process after "Application startup complete" (`/proc/<pid>/status`, `smaps`): `VmRSS` 31.6 GiB =
  `RssFile` 27.5 GiB (two mappings of `/dev/nvidiactl`, 23.8 and 3.0 GiB, fully resident) + `RssAnon` 3.8 GiB (heap
  2.7 GiB) + `RssShmem` 0.3 GiB. None of the mapped weight files in `/models` is resident.
- Peak while the weights load: `RssAnon` 6.4 GiB on top of the 27.3 GiB, 33.7 to 33.9 GiB in total. In the speed tests that
  followed, which included a 102k-token prompt, `RssFile` stayed at 27.3 GiB and `RssAnon` at 3.7 to 3.8 GiB.
- `VLLM_PLE_CPU_OFFLOAD: "0"` on one GPU does not start: `torch.OutOfMemoryError: CUDA out of memory. Tried to allocate
  800.00 MiB. GPU 0 has a total capacity of 94.97 GiB of which 665.56 MiB is free ... this process has 94.31 GiB memory in
  use` while the weights load. The table does not fit next to the 71.71 GiB of weights. The two-GPU profile can keep it in
  GPU memory (see its journal of 2026-11-20).

## The container's memory accounting

Under the heavy load (3 rounds of 16 requests at once: 15 with about 6k-token prompts and 1,500 output tokens, plus one
with a 100k-token prompt, 605 output tokens/s, KV cache usage up to 96 %), the container's cgroup showed:

| | |
|---|---|
| `memory.max` | 51,539,607,552 (48 GiB) |
| `memory.current`, highest sample | 20.42 GiB |
| `memory.peak` | 25.67 GiB |
| `memory.stat` | `anon` 6.34 GiB, `file` 13.94 GiB (page cache of the weight files, reclaimable), `shmem` 0.34 GiB |
| `docker stats` | 7.1 GiB / 48 GiB |

The 26.8 GiB table is not charged to the cgroup on this host (kernel 7.0, NVIDIA driver 595.71.05), so a container limit does not
hold it. On a host that does charge it the container would count about 31.6 GiB (33.9 GiB at the peak) plus page cache against
the limit: the 2026-11-20 journal of the two-GPU profile describes a container that sat at its 48G limit with the offload.

## The figures

| Figure | Before | After | Why |
|---|---|---|---|
| `deploy.resources.reservations.memory` | 24G | **36G** | measured 31.6 GiB at rest, 33.9 GiB at the peak, plus about 2 GiB |
| `hardware.memory.host_bytes` (ai-deploy.yaml) | 48 GiB | **36 GiB** (38,654,705,664) | the same figure: what a replica takes from the host |
| `deploy.resources.limits.memory` | 48G | **40G** | above the booking, for hosts that charge the table; the heavy load stayed far below it |

Two replicas of this profile need about 63 GiB of host RAM and do not fit a 61 GiB host. `VLLM_PLE_TABLE_MEMORY=shared` (one table per host in `/dev/shm`, shared by TP1 replicas) would let several fit; it was
not tested here.

**Planned:** sharing one PLE table between replicas is the way to make two replicas of this profile fit a 64 GB machine
in the future. If it works across containers, a second replica would add about 4 GiB (its own heap) instead of about
31 GiB, so two replicas would need about 40 GiB. That is not measured yet: a measurement is planned (platform-alpha
issue 378), and using it in the platform needs a node-managed shared memory volume and a booking that counts the shared
table once (host RAM proposal, phase 7). Until then, a machine of this size runs one replica of this profile.
