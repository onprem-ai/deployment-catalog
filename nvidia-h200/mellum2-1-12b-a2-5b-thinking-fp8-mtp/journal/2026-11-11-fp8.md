# 2026-11-11 - FP8 on One H200

**Goal:** Find a faster setting than JetBrains' BF16 command on one H200, for one user and
under load. Test service on inference node `nebius-e00pn5kkfnayh8wn6j` (H200 143,771 MiB),
vLLM v0.32.0, draft `drafts/mellum-h200-tune`.

## Result

Online FP8 (`--quantization fp8_per_block`): weights and activations in FP8 with
128x128-block scales, made from the BF16 checkpoint at load time. Probe (engine reached
directly, 10 s warm-up, 30 s window, about 320-token prompts, 512 tokens out), output
tokens/s at 1 / 32 / 128 requests at once:

| Setting | Free text | Code editing |
|---|---|---|
| BF16 (JetBrains' command) | 358 / 3,823 / 10,923 | 358 / 4,369 / 6,758 |
| FP8 | 376 / 5,461 / 13,124 | 376 / 4,915 / 8,738 |

Answers: 40 of 40 short questions with known answers (arithmetic and Python, 4 repeats,
thinking on) correct with BF16 and with FP8. A hidden fact was found at 6K, 25K, 50K and
94K prompt tokens with FP8. Start-up: FP8 weights 11.6 GiB less than BF16, KV cache 42.5 GiB
instead of 31.7 GiB (2,275,578 tokens instead of 1,698,091).

## Also tried, not kept

- ngram speculation (5 tokens): 2x for one user on code editing, but 36% slower on free
  text and 82% slower at 128 requests.
- Suffix decoding (vLLM `suffix`, needs Arctic Inference: image
  `onpremai/vllm-arctic:v0.32.0-arctic0.1.1`): up to 3.2x for one user on code editing,
  but the probe sent the same edit in every request, which suffix decoding caches, so the
  gain is overstated; free text 45% slower for one user. A batch-size-dependent draft
  length crashes vLLM 0.32.0 with suffix decoding (`AssertionError` in
  `suffix_decoding.py`). Not kept until measured on unique tasks.
- 256 requests and 16,384 batched tokens: no gain, failed requests at 128.
