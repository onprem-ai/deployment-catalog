# 2026-11-12 - Copy for One H200

**Goal:** The official catalog's RTX PRO 6000 Blackwell card (`nvidia-rtx-pro-6000-blackwell/nomic-embed-v2-moe-q8`)
as a card for one H200, then a first deployment.

## Changes from the Blackwell card

- `hardware.gpu.product: nvidia-h200`; the format's v1.1.0 schema.
- **Image:** the Blackwell card runs `onpremai/llama-cpp-blackwell`, a self-built llama.cpp image
  for SM120 (journal of `qwen35-122b-a10b-q4km`: built without `GGML_CUDA_FORCE_CUBLAS` against FP16
  overflow on Blackwell). The H200 (SM90) needs no special build, so this card runs llama.cpp's own
  CUDA server image `ghcr.io/ggml-org/llama.cpp` (release b9294), pinned by the digest the catalog's
  `qwen35-122b-a10b-q4km` card already uses.
- **Weights:** the Blackwell card reads an onprem-ai mirror
  (`nomic-ai--nomic-embed-text-v2-moe-GGUF--nomic-embed-text-v2-moe.Q8_0`). This card takes the same
  file from its publisher, `nomic-ai/nomic-embed-text-v2-moe-GGUF` at
  `ffbcf4c99e5d617dda10ec8c0e9f75754b0cbb80`: only `nomic-embed-text-v2-moe.Q8_0.gguf` (512 MB,
  Apache-2.0); llama.cpp reads the tokenizer and pooling from the GGUF file.
- Everything else as on Blackwell: `llama-server --embedding`, all layers on the GPU, flash
  attention, 512 tokens of context, 2 GiB hardware booking, and the passthrough API under
  `/{routing_model_id}` with `POST /v1/embeddings`. llama.cpp has no GPU memory share to set, so the
  card states no engine booking.

Nomic's model card asks for task prefixes: `search_query: ` for queries, `search_document: ` for
documents. The model is trained for Matryoshka truncation from 768 to 256 dimensions.

## First deployment

Deployed on one H200 (inference node `nebius-e00pn5kkfnayh8wn6j`), next to a Nemotron 3.5 Super VL
replica on the same GPU. Ready 60 s after the deploy.

- llama.cpp b9294 found the GPU (`CUDA0 : NVIDIA H200`; built for compute capabilities up to 1200,
  SM90 included) and ran with 4 parallel slots of 512 tokens. The process held 0.97 GiB of GPU
  memory, within the 2 GiB hardware booking. llama.cpp warns that the GGUF has no newline and no
  mask token in its vocabulary; embeddings are unaffected.
- Through the API gateway's passthrough path `/nomic-embed-v2/v1/embeddings`, with Nomic's
  `search_query: ` and `search_document: ` prefixes: vectors of 768 values with length 1.0. Cosine
  similarity to "What causes the northern lights?": the English answer 0.69, the German answer
  0.33, "Zurich is the largest city in Switzerland." -0.04: ranked right.
- The first requests after the start are slow (15.7 s, then 6.8 s for 33 texts) while CUDA
  compiles its kernels; after that, 33 texts (527 tokens) take 0.22 to 0.25 s.


## Measured use under load (2026-11-12)

Alone on one H200 (inference node `nebius-e00pn5kkfnayh8wn6j`), with a load probe on the node sending
straight to the engine: unique texts (no cache hits), 10 s of warm-up, then a 25 s window per level;
the GPU's memory read with `nvidia-smi` every 0.5 s. Short: 32 texts of about 80 tokens per request;
medium: 8 texts of about 500 tokens; longest: one text near the card's context length.

GPU memory: 905 MiB right after start, **983 MiB at the peak** (0.96 GiB), within the
2 GiB hardware booking. The memory does not grow with load: the engine reserves its KV cache at
start.

A first run with the card as copied failed at 16 requests of 32 short texts: the kernel killed
`llama-server` for memory (exit 137, `oom-kill:constraint=CONSTRAINT_MEMCG`, error report
`01a1d07b-12d7-70e3-80be-bcf8b908a6f1`). llama.cpp b9294 keeps a prompt cache of up to 8 GiB of host
memory by default, and the container may use 4 GiB. `--cache-ram 0` switches the cache off (an
embedding request reads its text once); with it the run above passed with no error, and the
container used 1.1 GiB of host memory.

## Bookings from the measurements (2026-11-12)

- GPU: no engine booking (llama.cpp), hardware 2 GiB (unchanged); engine booking about the measured use (fixed memory plus a KV cache for about two
  full-length requests), hardware booking about 1 GiB above the measured peak.
- RAM: the container used at most 1.2 GiB under load; reservation 2G, limit 3G, and
  `hardware.memory.host_bytes` set to the limit.
- CPU: the container used at most 2.0 cores under load (full saturation); reservation 2 cores
  (all six H200 embedding cards together reserve 12 of the VM's 16 vCPUs), limit 4.
