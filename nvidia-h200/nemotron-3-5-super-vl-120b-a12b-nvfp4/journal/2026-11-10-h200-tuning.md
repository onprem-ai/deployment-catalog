# 2026-11-10 - H200 Tuning, GPU Memory and Benchmark

**Goal:** Make the card faster on one H200 and record its measured GPU memory, following
the `optimize-model` and `measure-gpu-memory` skills. Draft `drafts/nemotron-h200-tune`,
test service `895e322f-6e4a-42f0-abf3-abe1053c9a6a` (model name
`nemotron-3.5-super-vl-tuning` while tuning) on inference node `nebius-e00pn5kkfnayh8wn6j`
(Nebius spot VM, 1x H200 143,771 MiB, driver 580.173.02), vLLM v0.32.0.

## Result

Two changes against NVIDIA's single-H200 recipe:

- `--compilation_config.max_cudagraph_capture_size 512` (was 256). With MTP every request
  takes 1 + draft tokens per step, so 256 graph tokens covered only 64 requests with 3
  draft tokens; above that the engine ran without CUDA graphs.
- MTP `num_speculative_tokens` 2 (was 3).

Plus the bookings: engine booking 118 GiB, hardware booking 131 GiB (was one 125 GiB
booking, see "GPU memory").

Full replica benchmark of the committed `compose.yaml` (job
`08d94c75-0342-46c0-881d-e77fb7c88a53`, replica `96e23dc6-780e-46d2-9d75-629826933a9d`,
2026-11-11 00:01 to 00:55Z, no request failed; `benchmarks/2026-11-11-llmperfbench.yaml`),
against the first benchmark of the published card (125 GiB, MTP 3, CUDA graphs 256). A
first run of the same settings under the tuning model name (job `93561265`, 2026-11-10
22:33 to 23:26Z, `benchmarks/2026-11-10-llmperfbench.yaml`; its `compose_sha256` is of the
compose file with the tuning name) agrees within 1 to 3% at every level.

token fewer than MTP 3.

## GPU memory

Before this session the card had no engine booking: vLLM was told the whole 125 GiB
hardware booking (`Desired GPU memory utilization is (0.8941, 125.0 GiB)`) and the replica
held 145,445,879,808 bytes (135.46 GiB) after its benchmark, above its booking
(`vram_used_above_allocated: true`). The engine booking is now 118 GiB (vLLM share 0.844)
and the hardware booking 131 GiB.

Measured on the committed settings, `vram_used_bytes` read every 30 s through
`inference_services_read get` during the full benchmark of 2026-11-11: peak
133,179,637,760 bytes (124.03 GiB), reached at 00:31:59Z (end of max-decode) and held to
the end. The first run of the same settings peaked at 122.96 GiB.

| Part | GiB | Source (deployment log of replica `96e23dc6`) |
|---|---|---|
| `model_weights` | 71.36 | `Model loading took 71.36 GiB memory`; the MTP layer is inside the main weight files, so no `drafters` part |
| `cuda_graphs` | 1.20 | `CUDA graph pool memory: 1.2 GiB (actual)` |
| `kv_cache` | 38.17 | `Available KV cache memory: 38.17 GiB`; `GPU KV cache size: 8,053,536 tokens` |
| `runtime_overhead` | 13.30 | the peak minus the other parts |

Engine budget from the log: `Desired GPU memory utilization is (0.844, 117.99 GiB)`, the
engine booking. Headroom to the hardware booking: 6.97 GiB. Overshoot above the engine
booking: 6.03 GiB. Loading time: about 5 minutes from redeploy to ready (`init engine ...
took 175.86 s`, compilation 29 s).

A memory-only round (max-decode to concurrency 64, cancelled after 14 minutes) on MTP 3
and CUDA graphs 256 peaked at 123.03 GiB, the same range.

benchmark with max-decode and mixed-load (about 45 minutes each); from round 4 a short
probe sends streaming requests (about 320-token prompt, 512 tokens out, thinking off)
straight to the engine over an SSH tunnel: 15 s warm-up and 45 s measured per level.

## The 126-request cap

vLLM's scheduler shows `Running: 126 reqs, Waiting: N reqs, KV cache usage: 99.6%` at 128
requests and more, with 8.05 million tokens of KV cache and only about 0.1 million in use.
The hybrid model's KV cache groups use 4,352-token blocks (`Setting attention block size
to 4352 tokens to ensure that attention page size is >= mamba page size`), and each
request holds one Mamba state block per group, so the pool runs out of blocks, not of
tokens. Prefix caching off changes the group sizes but not the cap. More memory raises it
(146 requests with a 124 GiB engine booking) but costs throughput at 128; `--mamba-block-size`
does not change the 4,352-token block. Raising it further needs a vLLM change.

## What did not work as planned

- The replica benchmark refuses a routable test service even with its own model name, so
  every round ran with `measure_while_serving_clients` true; no client used the tuning name.
- The spot VM was preempted once before the session (during the weight download) and came
  back on another GPU (`GPU-266f47cf...` to `GPU-ce2fb271...`); the replica was moved with
  `set_replicas`.
